Webhooks

Receive real-time email delivery event notifications via webhooks.

Webhooks

Webhook destinations must use HTTPS on port 443, without credentials in the URL, and resolve exclusively to public IP addresses. Private, loopback, link-local and reserved addresses are rejected on every delivery. Redirects are not followed; configure the final endpoint URL. Deliveries have a 10-second deadline. These rules apply to test deliveries too.

Webhooks deliver real-time HTTP POST notifications to your server when email events occur (delivery, bounce, open, click, etc.). Use webhooks to update your application state, trigger workflows, or monitor deliverability.

Tier requirement: Webhooks are available on Starter ($5/mo) and above: 1 endpoint on Starter, 3 on Micro, 10 on Pro, unlimited on Scale.

Payload Format

Every webhook is an HTTP POST with a JSON body. All events share this envelope:

FieldTypeDescription
eventTypestringOne of the event types. Also sent in the X-NorthRelay-Event header.
messageIdstringFor email.* delivery events, the message id. For contact, list and engagement events, a unique id for this event.
timestampstringISO 8601 time the event was generated
recipientstringRecipient (or contact) address, when there is one
senderstringSender address (email.* delivery events)
subjectstringSubject line (email.* delivery events)
statusstringDelivery status, for example delivered or dropped
smtpResponsestringResponse from the receiving server, when available
bounceReason, bounceTypestringBounce details on email.bounced and email.dropped, when available
detailsobjectEvent-specific data. For delivery events this is the raw event from the mail server; for the events below its shape is documented.

Fields that do not apply to an event are omitted. Each request also carries X-NorthRelay-Delivery (a unique id per delivery attempt) and X-NorthRelay-Signature.

Contact, List and Engagement Events

These events let you keep your own application in sync with subscriptions and engagement. They fire for every path that changes a subscription: hosted signup forms, the Subscriptions API, list member changes, unsubscribe links, RFC 8058 one-click unsubscribes and the hosted preference centre. CSV imports and direct contact edits (POST or PATCH /contacts) do not fire them.

contact.subscribed

Someone subscribed, joined lists through a subscribe call, or opted back into a topic.

details fieldDescription
contactId, emailThe contact
sourceFORM, API, IMPORT, PREFERENCE_CENTER, PLATFORM_SIGNUP or DASHBOARD
listIdsLists the contact was asked to join (may be omitted or empty)
topicIdsTopics the contact opted (back) into (may be omitted or empty)
requiresConfirmationtrue while a double opt-in is outstanding; wait for contact.confirmed
statusContact status after the change: PENDING or ACTIVE
formId, listId, fieldsSignup-form submissions only: the form, its list (kept for older consumers) and the submitted fields

contact.confirmed

The recipient clicked the double opt-in link.

formId is null when the subscription came from the Subscriptions API.

contact.unsubscribed

The recipient unsubscribed from everything, from one list, or from one topic. Fires even when the recipient is not one of your contacts (for example an unsubscribe from API-sent marketing mail).

details fieldDescription
contactEmailThe address that unsubscribed
contactIdThe contact, or null when the address is not a contact
scopeall (no marketing mail at all), list or topic
listIdThe list left, for scope: "list"
topicIdThe topic opted out of, for scope: "topic"
methodone_click (mailbox provider button, or the button on NorthRelay's hosted unsubscribe page), link (your own unsubscribe page via POST /unsubscribe), preference_center, api, dashboard, platform_settings or complaint
campaignIdThe campaign the unsubscribe came from, when known
reasonFree text, when given
categoryLegacy alias of topicId, kept for existing consumers

list.member_added and list.member_removed

A contact joined or left a list. list.member_removed fires both when a recipient unsubscribes from a list (or from a topic the list is tagged with) and when you remove a member.

source is the subscription source (FORM, API, IMPORT, PREFERENCE_CENTER, PLATFORM_SIGNUP, DASHBOARD), or UNSUBSCRIBE when the recipient left by unsubscribing. Owner removals through the API use API.

email.opened and email.clicked

A person opened a message or clicked a tracked link. Opens and clicks classified as bots (security scanners, link prefetchers, privacy proxies) are not sent. They fire for campaign mail and for API mail with tracking: marketing-stream API mail is tracked by default (opt out with track: false), transactional API mail only with track: true.

details fieldDescription
emailRecipient address
contactId, campaignIdSet for campaign mail
trackingIdSet for API mail: the tracking id of the sent message
urlThe clicked link (email.clicked only)
userAgentClient user agent, or null
engagementTypeAlways HUMAN

For API mail, email.opened fires once per message and recipient; repeat opens are not sent. Clicks fire every time. For campaign mail every human open is sent.

Signature Verification

Every webhook request includes an X-NorthRelay-Signature header containing an HMAC-SHA256 signature computed from the raw request body and your webhook secret.

Always verify signatures to ensure requests originate from NorthRelay and have not been tampered with.

Verification Algorithm

  1. Extract the X-NorthRelay-Signature header value
  2. Compute HMAC-SHA256 of the raw request body using your webhook secret as the key
  3. Compare the computed signature with the header value using a timing-safe comparison

Retry Policy

If your endpoint does not respond with a 2xx status code within 10 seconds, NorthRelay retries the delivery:

AttemptDelay
1st retry30 seconds
2nd retry2 minutes
3rd retry15 minutes
4th retry1 hour
5th retry4 hours

After 5 failed retries, the event is marked as failed. Failed events are visible in Dashboard > Webhooks > Event Log for 30 days.

Best Practices

  1. Respond quickly. Return 200 immediately and process the event asynchronously. Do not perform heavy work in the request handler.
  2. Handle duplicates. Deduplicate on eventType, messageId and recipient. The same event may be delivered more than once, and a contact change can arrive before or after a related list.* event; read the current state with GET /subscriptions/{email} when order matters.
  3. Verify signatures. Always validate the X-NorthRelay-Signature header.
  4. Use HTTPS. Webhook URLs must use HTTPS. HTTP endpoints are rejected.
  5. Log failures. Monitor your webhook endpoint health in the dashboard.
